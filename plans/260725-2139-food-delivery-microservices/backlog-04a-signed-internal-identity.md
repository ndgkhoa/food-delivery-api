- **Brief**: Today the gateway is the single trust boundary: it verifies the JWT and stamps `x-tenant-id`/`x-user-id`/`x-roles` (`applyTrustedIdentityHeaders`, `http-forwarder.ts:80`); every downstream service **trusts those headers unconditionally** (`TrustedIdentityInterceptor`) on network isolation alone. Any caller that reaches a service directly (a compromised pod, a mis-scoped NetworkPolicy, a port-forward) can forge `x-tenant-id`/`x-roles` and act as any tenant/role — a full cross-tenant + privilege-escalation bypass. Fix: the gateway **HMAC-signs** the identity it stamps; each service **verifies** the signature before trusting the headers, failing closed (401) on a missing/invalid/stale signature. Defense-in-depth on top of 04b's network isolation — neither alone is sufficient.

## Key decisions
- **HMAC-SHA256 over a canonical identity payload + timestamp.** Shared secret `INTERNAL_IDENTITY_SIGNING_KEY` known to the gateway and every service. Canonical string = `tenantId\n sub\n roles(joined)\n ts` (the EXACT values stamped, so a tampered header breaks the MAC). Sign → stamp `x-identity-ts` + `x-identity-sig` (hex). Verify → recompute + `crypto.timingSafeEqual` (constant-time; never `===` on the hex).
- **Replay window.** The signed `ts` (epoch ms) is checked against `now` within `INTERNAL_IDENTITY_MAX_SKEW_MS` (default 60000). A captured header replayed later than the window → rejected. Generous window tolerates k8s clock skew; internal-only so the risk is already low.
- **Fail closed, but only where enforced.** Enforcement = `NODE_ENV !== 'test'` AND `INTERNAL_IDENTITY_SIGNING_KEY` is set. In prod/dev-serve (key set, not test) a missing/invalid/stale signature → **401** BEFORE the tenant context is established (a request must never run unscoped OR mis-scoped). Under `NODE_ENV=test` enforcement is OFF so the existing per-service suites (which stamp raw identity headers with no signature) stay green; the signer/verifier + the enforced reject paths get their OWN dedicated shared-tenancy unit tests that force enforcement on. This mirrors the OTel `register.ts` "reads straight off `process.env`" pattern — the verifier reads the key/NODE_ENV/skew from `process.env` (not a service-specific validated schema) so shared-tenancy stays decoupled from any one service's config.
- **Verifier is a small pure class**, `IdentitySignatureVerifier` (`{ key, enforced, maxSkewMs }` → `verify(headers, now)` → ok / reason), provided by `TenancyModule` via a factory that snapshots `process.env` once. The interceptor injects it and calls it right before establishing context. Pure + directly unit-testable (no Nest bootstrap needed for the reject-path tests).
- **Signer stays in the gateway forwarder.** `applyTrustedIdentityHeaders` gains an optional `signer?: (identity, ts) => string` param; when provided it also stamps `x-identity-ts`/`x-identity-sig`. The forwarder builds the signer from `INTERNAL_IDENTITY_SIGNING_KEY` (via ConfigService) and a monotonic `Date.now()`. When the key is unset (never in prod), it stamps identity unsigned exactly as today (dev without the key still works; services with enforcement off accept it).
- **Base env-schema owns the key.** Add `INTERNAL_IDENTITY_SIGNING_KEY` (optional string, min length 32 when present) + `INTERNAL_IDENTITY_MAX_SKEW_MS` (default 60000) to `baseEnvSchema` so the gateway (via its `.omit/.extend`) and every service inherit it. A dev default value is fine (documents the contract); prod supplies a real secret via a K8s Secret. NOT a `.min(1)`-required var — an unset key means "unsigned/unenforced" for local one-off runs.
- **K8s**: `INTERNAL_IDENTITY_SIGNING_KEY` becomes a Secret key referenced by the gateway Deployment AND every service Deployment (all must share the same value). Add to the base Secret manifest (placeholder) + note in the prod overlay that it must be a real generated secret. Same value everywhere or every request 401s — call this out loudly in the manifest comment.

## Success criteria
- A request through the gateway carries a valid `x-identity-sig`; every service's **HTTP edge** accepts it and establishes the correct tenant/roles. (The gRPC east-west edge is out of 04a scope — covered by 04b NetworkPolicy; see H2.)
- A direct-to-service **HTTP** request (bypassing the gateway) with forged `x-tenant-id`/`x-roles` and NO valid signature → **401** (enforced env) — the spoof is rejected before any tenant scope is set.
- A replayed captured header older than the skew window → 401.
- The existing per-service test suites (raw identity headers, `NODE_ENV=test`) stay green (enforcement off in test); shared-tenancy has NEW tests proving the enforced reject paths.

## Risk assessment
| Risk | L×I | Mitigation |
|------|-----|-----------|
| Key mismatch gateway↔service → every request 401s | M×H | Single shared Secret value; loud manifest comment; dev default keeps local green; enforcement auto-off in test |
| Clock skew across pods rejects valid requests | L×M | 60s window (`INTERNAL_IDENTITY_MAX_SKEW_MS`), tunable; k8s node clocks are NTP-synced |
| Non-constant-time compare leaks the MAC | L×M | `crypto.timingSafeEqual` on equal-length buffers, never string `===` |
| Existing test suites break on the new check | M×M | Enforcement gated off under `NODE_ENV=test`; new coverage lives in shared-tenancy with enforcement forced on |
| Rollout ordering (services enforce before gateway signs) | M×M | Deploy gateway (signs) first, then flip service enforcement — but enforcement is env-driven, so a single shared key present everywhere makes it atomic; note in the runbook |

## Security considerations
- The signing key is a shared secret — MUST be a K8s Secret (not a ConfigMap), never committed. Rotating it requires updating the Secret + rolling all pods (brief window where old/new coexist → keep the skew window; a rotation runbook is 04c-adjacent, note it).
- The MAC binds tenantId + sub + roles + ts — tampering any of them (e.g. escalating `x-roles`) breaks verification. It does NOT provide confidentiality (headers are plaintext) — that's fine, they're not secret; it provides integrity + authenticity, which is the threat (forgery/escalation).
- Fail-closed: a verification failure denies the request; it never falls back to trusting the unsigned headers when enforced.
